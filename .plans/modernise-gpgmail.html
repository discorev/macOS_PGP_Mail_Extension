Plan · macOS_PGP_Mail_Extension

Getting GPGMail working again on macOS 27

The old compose crash doesn't reproduce on macOS 27, so this is a modernise-and-fix job: split out a platform-neutral core, fix the bugs we found, and add the missing UI. It's not a rescue.

Effort ~1 day of agent time Files ~20 touched, 6 new Risk medium: Mail's line-ending behaviour, Libmacgpg longevity Platform macOS only (MailKit is API_UNAVAILABLE(ios))
What the repro told us

Evidence so far

  • Builds cleanly on Xcode 27 against Libmacgpg 1.5.1
  • Compose, 60s autosave and ⌘S, with signing on: no crash
  • Mail 27 saves drafts without calling encode, so the old crash path has gone
  • Sign toggle lights up for an address that has a key
  • Encrypt is always greyed out: it checks canEncrypt on the primary key, but modern keys encrypt with a subkey
  • Decode path can crash: ValidSignature force-unwraps algorithm IDs, plus several as! and ! on Mail input
  • Signature details view and host app are empty stubs
  • Not yet tested end to end: actually sending a signed/encrypted mail, then decrypting it
  • Two incoming shapes must both decrypt: inline PGP (A&A support: armour inside a single text/plain body) and PGP/MIME (A&A invoice: multipart/encrypted, partial-length packets, ~88 KB with an attachment inside)
  • Both A&A originals decrypt with your imported Keybase key (…F0022C3BE595C085). Inline decrypts to bare LF text with no MIME headers; PGP/MIME decrypts to a CRLF multipart/mixed with base64 text + a PDF
  • Both are signed by A&A's key 2BC593F64AD8A132, which isn't in your keyring: gpg reports ERRSIG NO_PUBKEY and exits 2 even though decryption succeeded

Weakest part of the plan
A1

Which GPG engine sits behind the core

Libmacgpg is a GPG Suite binary from 2022 and isn't open to us. If GPG Suite stops shipping it, the extension breaks. Either way it goes behind a small PGPBackend protocol, so it can be swapped later or for iOS.

A2

Where the platform-neutral core lives

This is your "keep the door open" for iOS. MIME parsing and PGP/MIME assembly must never import MailKit, AppKit or Libmacgpg.

A3

Encrypting to yourself

Today it encrypts only to recipients, so your own Sent copy can't be read, by you or by a future iOS reader.

Section C · mechanical
Bug fixes and cleanup (trust me)
  • Key choice uses canAnySign / canAnyEncrypt and skips expired, revoked and disabled keys
  • Email matching ignores case on both sides (today only Mail's side is lowercased)
  • One shared GPGKeyManager with a cached email→key index. The decoder stops building a new manager for every message
  • Remove every ! / as! on external input: ValidSignature, rawData!, primaryUserID.name!, the statusDict casts
  • Unknown signature or hash algorithms decode as "unknown" instead of crashing
  • Encryption failures report an encryption error, not signingFailed
  • Judge results from gpg status lines, not the exit code alone: DECRYPTION_OKAY + ERRSIG NO_PUBKEY means "decrypted, signed by an unknown key" (shown in the panel), not a failure. gpg's stderr goes into real error messages
  • print → os.Logger (subsystem com.olliespage.GPGMail)
  • Accept Version: 1 with CRLF, LF or trailing whitespace
  • Fix typos in type names (BadSignaure, primaryKeyFingerpring). The GPGMailExtention bundle ID stays, so Mail doesn't re-register the extension
  • Update the README for the current setup
Assumptions I'm making
  • GPG Suite stays installed. Its ~/.gnupg keyring is the source of truth.
  • Builds are signed with your personal team (D6AAJCLH87). No notarisation or App Store work this round.
  • The throwaway test key (17AC…78F2, expires 24 Oct) stays until step 6 so it can be reused for verification, then I delete it. That's later than I first said.
  • You'll delete the leftover "draft autosave test" draft in Gmail yourself.
  • No iOS target, and no crypto library swap, this round.
  • Your real A&A emails stay out of the repo. Tests use synthetic look-alikes built from their structure, without your addresses or headers.
